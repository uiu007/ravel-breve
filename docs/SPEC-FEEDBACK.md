## SF-01 `3 3 =` 与 REQ-01 镜像规则矛盾（**缺陷**，CHK-1）

- **位置**：REQ-05 验收标准（「`3 3 =` 得 `true`」）。
- **现象**：REQ-01 规定一行内**从右向左**求值。`3 3 =` 的最右 token 是 `=`，
  按镜像规则它**最先**执行 → 此时栈为空 → 必然栈下溢（退出码 30），不可能得 `true`。
  正确写法是 **`= 3 3`**。
- **佐证**：规格自身的修订表（附录 E 第 1 行）已把 `double : [ 2 * ]` 改为 `[ * 2 ]`，
  即承认「镜像后语义必须成立」；REQ-05 的这处示例是同一类问题的遗漏。
- **建议**：把 REQ-05 验收标准改为「`= 3 3` 得 `true`；`3 3 =` 为栈下溢（反例）」。
- **实现现状**：实现按镜像规则执行（`= 3 3` → `true`；`3 3 =` → 30），
  并在 `tests/conformance/req-01-notation.janet` 里把「后缀写法不成立」写成**正面验收**。
- **裁决**：CHK-1。**v1.0c 处置**：已修正（REQ-05 + §4.9.1）。

## SF-11 `split` 的元数（**留白**，CHK-2/M2）

## SF-12 组合子引号里隐藏实参的位置（**留白**，CHK-2/M2）

- **位置**：附录 A 的 `map [q] seq` / `filter [q] seq` / `fold [q] init seq` / `keep [q] X`。
- **现象**：规格只说「引号作用在同一数据栈上」，未说**隐藏实参补在引号波兰式的哪一端**。
- **实现现状**（由 §4.9.1「最左实参 = 最后入栈 = 栈顶」导出，D-18）：
  引号是**未写满的波兰表达式**，隐藏实参补在**最右**：
  `filter [ < 2 ] { 1 2 3 4 }` ≡ `< 2 元素` → `(3 4)`；`map [ - 10 ] { 1 2 3 }` ≡ `- 10 元素` → `(9 8 7)`。
  直接推论：**栈上已有的值只能落在最右操作数位置**；要让它当第一个操作数须 `swap`。
- **建议**：附录 A 每个组合子补一行「补完后的波兰式」，例如
  `filter [ < 2 ] seq  ⇒  对每个元素 x 求值 < 2 x`。
- **影响**：这是本方言**最容易误读**的一点，直接决定所有组合子用例的期望值；
  若改为「补在最左」则全部组合子语义翻转。

## SF-13 语句内「先执行词、后压字面量」的直觉冲突（**留白**，CHK-2/M2）

- **位置**：§4.9 镜像规则。
- **现象**：`7 fail "boom"` 中 `7` **不会**先入栈（镜像后 `fail` 先执行）；要「先压 7 再失败」必须分语句
  （`try [ 7\nfail "boom" ] …`）。
- **实现现状**：分语句写法（D-19）。
- **建议**：规格补一条：**一条语句内的求值序是书写序的完全镜像**，因此「压栈副作用」也按镜像序发生；
  需要先后次序时用换行分语句（REQ-40）。

## SF-14 附录 A 的词形次序与 D-18 推论冲突（**需修订规格**，M3）

- **位置**：附录 A 词表里 `send` / `resend` / `append` / `bcast` 的栈效应写作
  「`Agent Utter`」「`Agent Utter`」「`Agent Utter`」「`Domain Utter`」（目标在前）。
- **冲突**：D-18（组合子引号 = 未写满的波兰表达式，隐藏实参补在**最右**）的推论是
  **栈上已有的值只能落在最右操作数位置**。agent 是栈上的变量（REQ-30），若写成「目标在前」，
  则 `send say "hi"`（想发给栈上的 agent）会**把 utter 当目标**，必须每处都 `swap`。
- **实现现状（D-26）**：词形改为 **`Utter` 在前、`Agent`/`Domain` 在后**：
  `append Utter Agent -- Agent`、`send Utter Agent -- Stream`、`resend Utter Agent -- Stream`、
  `bcast Utter Domain -- list Stream`。
- **建议**：规格把附录 A 这四行改为 `Utter` 在前，并在 §4.9 补一句推论
  「凡『目标』是栈上变量者，一律作最右实参」。

## SF-18 compact 主判据对小工作区过于敏感（REQ-21）

- **位置**：REQ-21 条件 ①「日志 > 快照的 0.5 倍」。
- **现象**：小工作区（十来个词）快照 ~150 字节、一行日志 ~110 字节 → 几乎每轮都 compact，
  「增量日志」实际上退化成「每轮全量重写」，与 REQ-20 的意图（增量）相反。
- **当前实现**：按字面执行（D-37），并在文档里说明。
- **建议**：改为「日志 > max(0.5 × 快照, 512 字节)」，或把 ① 改为「日志 > 快照 0.5 倍 **且** 日志 > 32 行」。
  二选一都能保住「开销可预期」而不至于让增量失效。

## SF-22 附录 F 的「待冻结项」本实现的裁定（REQ-24）

- **位置**：附录 F 末尾列了 5 项待冻结：JSON 请求、分片粒度/背压、协议版本字段、错误对象细节、会话消息。

| 待冻结项 | v1 裁定 |

| JSON 请求 | `eval` / `ping` / `hello` / `reset` / `quit`；裸文本 = `eval` 简写 |

| 会话消息 | v1 只推 `chunk`/`close`；`@Toolcall` 等事件暂不进协议 |

- **建议**：把上表升为附录 F 的正式内容，避免每个实现各自冻结。

- **位置**：REQ-06 把 `Json` 列为结构类型；附录 A 的 L2 把它和 `Role` / `Content` 并列成
  「字段 / 类型（名词）」，但全文没给栈效应，也没说它取什么、断言什么。
  对照 `Role` / `Content` 都是**字段访问词**，`Json` 无从类比（`from-json` 已经产出宿主值）。
- **当前实现**：**不实现**（`Json` 报 20「未知的词」）；`Json` 只作为**类型名**存在于
  「宿主映射」表（`table` / `struct`）。符合性测试 `conformance/req-09-appendix-a.janet`
  显式断言它仍未知，等裁决后再补。

## SF-29 `if` 的「条件已算成值」写法与递归都没写进规格（附录 A · L5 / REQ-33）

- **现象一**：`if cond [ 真 ] [ 假 ]` 的镜像序是 `[假] [真] cond if`——cond **必须**由它自己的
  token 供操作数（如 `if < 2 [ … ] [ … ]` 里的 `2` 由语句自己压）。条件若**已**算成栈上的值，
  两个引号会压在它上面，`if` 拿到的是引号。规格没给这种情形的写法。
- **现象二**：REQ-33 只说「定义行在装载期注册」，没说**体内能否自引用**；
  实现按「先占位、再转译体」支持递归（D-51），否则 `fact : [ … fact … ]` 转译期就报 20。
- **当前实现**：转译期按「语句里只有词 + 引号」选 stack 变体
  （`if [ 真 ] [ 假 ]` / `when` / `unless` / `loop`），其余情形保持原形；递归可用。
- **建议**：附录 A 的 L5 补两行——① `if` 的两种写法与判据（条件内联 / 条件在栈上）；
  ② 定义行允许自引用（递归的求值深度上限如何处理，见 `depth` / 60 号编排错误）。

## SF-30 定义行没有写文档串的语法（REQ-34 / REQ-35）

- **位置**：REQ-34 把定义行固定为「恰好三个 token」（`名字 : [ 体 ]`）；REQ-35 要求
  `doc` / `see` 从字典读、字典条目「含文档串」。两者之间缺一条语法：文档串从哪来。
- **当前实现**：额外接受四 token 形式 `名字 : "说明" [ 体 ]`（D-52）；三 token 形式不变。
- **建议**：REQ-34 改成「定义行 = `名字 : [ 体 ]` 或 `名字 : "说明" [ 体 ]`」，顺手说明
  `see` 打印源、`doc` 打印说明。

## SF-31 附录 E 的 31「类型错误」覆盖不到越界/取值类宿主错误（REQ-41）

- **当前实现**：宿主原生错误一律归 31（D-53），30 只留给方言层的栈下溢。
- **建议**：附录 E 的 31 描述改成「类型 / 取值错误」，或单开 34 给越界。

## SF-32 附录 A 没有 provider 配置词（REQ-14 / REQ-37）

- **位置**：REQ-14 定义「工作区 = 字典 + 栈」，附录 A 的词表里没有任何**配置**词；
  provider / 模型只能靠进程环境变量（规格正文根本没提）。

- **建议**：附录 A 增一行「配置」；REQ-14 的工作区描述补一句「provider 配置属于工作区」；

## SF-33 规格未定义「失败的求值」对栈的影响（REQ-30 / 附录 E）

- **现象**：REQ-30 只说「下溢报 30」，没说报错后栈是什么样。实现里 `+ 1` 先压 `1`

- **建议**：REQ-30 补一句「失败的求值不改变栈」，或在附录 E 的 30/31 行注明。

## SF-34 真 provider 的错误响应形状没有约定（REQ-25 / 附录 F）

## SF-35 REPL 的编辑键位不在规格里（**留白**，CHK-7）

- **位置**：REQ-22（CLI 形态）/ §4.12 前后端分离；全文未提「REPL 怎么编辑一行」。
- **现象**：规格只规定「REPL 一次吃一行、栈跨行保留」。但实现要真正可用，

## SF-38 「模式"照抄名字"与"照抄语义"是两件事」（v1.0m / REQ-65 / REQ-66）

**来源。** 用户要求：「查看 DeepSeek harness 实现的全部模式（modes），并尝试复刻这些模式」。
读 dsh（`packages/bundle/web-app/presets/{standard,ptc,minimal,cordis}.patch.yml`、

2. **复刻四个预置**：`standard` / `ptc`（改）/ `minimal` / `cordis`，各自的人格提示、工具集、`:wire`。

3. **REQ-66**：dsh 的 plan mode 是**正交**的（`/plan` 进出，工具不换、只换提示，`exit_plan_mode`

4. **补两个 `tool-fs` 工具**：`read`（带行号 / `offset` / `limit`）与 `write`（原子替换），

5. **明确不复制**：`web` / `jobs` / `schedule` / `subagent` / `todo` / `present` / `plugin-market`

与 `fs-observation-policy`（"先读后改"的强制：这是**策略**，本仓把它留给模式提示，不做硬约束）。

## SF-39 「预置 = 工具清单」漏了一半：设定也是预置的一部分（v1.0n / REQ-67）

**现象。** D-72 照 dsh 的四个预置复刻了工具清单与人格，但漏了**预置同时决定的授权**：
`default` 声明 `shell`，`shell` 却要 `RB_ALLOW_SHELL=1`。缺省模式下模型第一次调它，
整个回合以 `@RoundDone 失败` 收场。

**为什么这是规格缺陷，不是实现 bug。** REQ-54 写「`shell` 默认关闭：需要 `RB_ALLOW_SHELL=1`，
所以它必须是**显式**选择」，REQ-65 写「`standard` = 完整文件工具 + `shell`」。
两条各自自洽，合起来要求用户"选了模式之后再手动补一个环境变量"——
**"模式的工具集"与"工具的可用性"是同一件事的两半**，规格把它们分在了两节，于是没人负责对齐。

dsh 那边不出现这个问题，是因为它的预置文件里 `tools` 与 `permissions`/`approval` 是**同一份 YAML**：
声明工具的地方就声明它怎么被允许。

**建议（v1.0n 采纳）。**

1. **REQ-67**：能力层声明前置设定表（`:tools/gates`）；模式声明带前置设定的工具时，
   必须把对应开关一起声明；缺省值进 `flag` 的缺省表。
2. **呈现层跟着设定走**：设定不满足 → 不上 `wire`（模型看不见 → 不会中途失败），
   但注册表保留（`invoke` 给点名到设定的 `60`）。
3. **可发现、可关**：`--modes` 印 `设定：allow-shell=on`；关闭有词（`flag-set`）与环境变量两条路。
4. **装载期告警**：模式声明了工具却没带设定 → stderr 一行（不改退出码）。

**规格写作上的教训。** 任何"某能力需要先满足 X"的条款，都必须同时回答
**"谁负责满足 X"**；否则它只是把责任推给用户。本仓的选择是：**满足者 = 声明该能力的模式**。

**状态**：v1.0n 已冻结（REQ-67，附录 T；REQ-54 的 `shell` 条款随之修订），实现见 D-73。
